# Prepared number-field multiplication, 2026-11-17 night sprint

Baseline production source is `ab22a4a22625f4beb2bd2a49b836f769c941ef90`.
This finite pass evaluates one mechanism: prepare the negative monic modulus
inside the checked opaque `Field`, then compute only a remainder after ordinary
`numberfield.multiply`'s polynomial product. The previous canonical add/sub and
coordinate changes remain intact. No public function signature or checker
algorithm changes.

## Code-grounded hypothesis and invariant

The old multiply path calls `poly.multiply`, then `element`, then generic
`poly.normal_form`/`poly.divide`. Generic division searches the single divisor,
rechecks multivariate exponent vectors and its leading coefficient, constructs
quotient terms that the caller discards, and negates a scaled modulus at every
cancellation. The candidate retains `poly.multiply`, uses a cached negative monic
modulus, and reuses `poly.scale` and `poly.add` for each leading cancellation.
It avoids quotient construction, repeated divisor discovery, and repeated modulus
normalization/negation. The fraction of original cost due to these actions was
not profiled, so no Amdahl bound is asserted in advance.

`Field` preparation happens only after the unchanged `minimal.check` succeeds
and degree is positive. Field identity still compares the complete original root
certificate, including its isolating interval. The cache is derived immutable
state and is never trusted as a certificate. `Element` is opaque; its existing
constructors and arithmetic guarantee canonical univariate residues of degree
below the modulus. `poly.multiply` preserves univariate canonical terms. Each
new reduction cancels the leading coefficient exactly and strictly lowers the
leading degree. `element`, generic polynomial division, and all independent
certificate checkers retain their old algorithms. Ordinary complex-field
multiplication reaches the new path through its four NF products.

The present minimal-certificate checker forces its result polynomial to equal
the monic selected factor (`realminimal/certificate.mbt` and
`realminimal/polynomial.mbt`). Thus an accepted nonmonic result modulus is not
currently constructible publicly. The cache nevertheless uses `poly.monic`;
new private-reducer tests compare rational nonmonic divisors with generic
normal form. Public tests cover normalization of a nonmonic raw definition and
unchanged rejection of a forged nonmonic certificate result.

## Frozen measurement and validation

Harness commit `d26d45b`, package `src/cmd/nightnfbench`, has six fixed cases:
dense quartic repeats, sparse no-reduction quartic products, degree-one
products, checked field construction only, field construction plus one product,
and complex squaring. Setup-only and one-shot loops include certificate
verification, cache preparation, public constructors, and complete result checks
inside the timer. Other repeat cases include their one checked setup in the
whole-process timer. No repeated-use claim may omit the setup controls.

The quartic field is `t^4-10*t^2+1`, root interval `(3,4]`; degree-one is `t`,
interval `(-1,0]`. Independent dense machine-integer schoolbook products and
monic long division compute all product expectations. Every iteration compares
the complete canonical polynomial or complete complex coordinate vector. Field
setup compares the complete original certificate, root certificate, modulus and
degree. Raw JSON includes every checked stdout, elapsed interval, source/harness/
executable hashes, compiler and CPU affinity. Five independent-process ABBA
blocks use the shared CPU4 lock, native release, prebuilt frozen executables.
Whole-process timing includes setup and verification; inner timing has the
explicit boundaries above. All heavy builds/checks/tests use the same lock,
`-j 1` (except `moon info`, which has no jobs option), and distinct build trees.

New tests compare 108 input pairs over dimensions 1, 2 and 4 with independent
machine-integer long division and the unchanged generic multiplication/remainder
path. They include raw high-degree inputs, zero, sparse coefficients, and
cancellation; existing Fraction oracle fixtures cover rational operands. They
also check nonmonic divisors, nonmonic raw definitions, distinct/refined selected
root intervals, rejected invalid certificates, and dimension/fuel errors.

## Results and decision

**Adopted**, source commit `ae808a4`. The ordinary repeated multiply paths and
the actual complex-field caller improve in every initial ABBA block. The cache
tradeoff is explicit: field setup allocates/prepares an additional immutable
polynomial; setup-only and one-shot benefits are unproven. This is not a claim
that all one-shot uses improve. No second code variant, new mechanism or broad
parameter search was attempted. The only permitted follow-up repeated the two
ambiguous controls with the exact same frozen executables and five ABBA blocks.
The pass stops after this decision.

Native release, CPU4 affinity on Intel Core Ultra 7 255H under Microsoft/WSL
virtualized Linux. Compiler: moonc v0.10.20+65efd5b93; moon 0.1.20261104. The
raw reports preserve full compiler and platform metadata. Ratios below are
before/after; above one favors the candidate. Process medians retain startup,
proof normalization, verification, preparation and full output checks. The field
setup/one-shot loops reuse an already normalized certificate: producing that
certificate is counted once in process timing, not repeated inside those loops.
They measure the public checked Field constructor, not regeneration of a new
irreducibility certificate for every multiplication.

Initial setup-only was about 3.9% slower; follow-up setup-only was about 3.7%
faster. Initial setup+one-shot was about 6.6% faster; follow-up was about 3.3%
slower. Their signs reverse, so neither absence of a preparation penalty nor a
one-shot speedup is established. Initial one-shot process ranges include a
528.815 ms baseline and 443.691 ms candidate outlier; they are retained in the
raw report. A guaranteed amortization count cannot be inferred by subtracting
these noisy different-case medians. The clear 1.222x dense-repeat and 1.209x
complex-square gains justify adoption for repeated field arithmetic despite
these uncertain setup/control outcomes. Sparse/no-reduction and degree-one
repeat gains also include the usual public context checks. No certificate or
verification cost was removed to obtain those ratios.

All 120 initial and 40 follow-up repeated outputs passed complete comparison.
NF+CF suites passed 173/173 on each of wasm, JS and native, all with
`--deny-warn`. Global all-target `moon check --deny-warn -j 1` passed (1,837
tasks); scoped all-target `moon info` passed (94 tasks); purity passed 328
production files. No tests/checkers were weakened. `git diff --check` passed.
Logs retain JS/native and global checks; the separately run wasm result is
recorded in the validation receipt.

No public function signature changed. The generated interface records only
that opaque `Field` has an additional private field. The cache is omitted from
field identity, certificate payloads, error/fuel decisions and returned numeric
values. No memory or large-degree performance claim is made; memory footprint
of the additional cached polynomial was not measured. The tested performance
fields have degrees 1 and 4, with exact integer fixtures; correctness also covers
degree 2, rational fixtures and nonmonic divisors. Other fields, hardware,
construction patterns and application totals remain unmeasured.
