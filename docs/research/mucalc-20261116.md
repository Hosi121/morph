# Modal μ-calculus の有限モデル検査（2026-11-16）

[ドキュメント](../README.md) / [研究・探索記録](README.md)

[研究記録](README.md) / [parity solver](parity-20261116.md) / [生成 API](../../src/mucalc/pkg.generated.mbti)

目的は、正の再帰を持つ NNF の modal μ-calculus を有限 Kripke 構造上でモデル検査し、既存の証拠付き parity solver へ接続すること。[compiler](../../src/mucalc/compiler.mbt) は状態×構文 occurrence の評価ゲームを作り、[solver wrapper](../../src/mucalc/solve.mbt) が勝者を各状態の充足判定へ戻す。凍結依存は parity commit `377a22d`。`src/parity` と共有 package は変更していない。

## API と入力の契約

`model(states)` → `compile(model, formula)` → `start(compilation)` → `run(machine, fuel)` → `holds(solution, state_id)` の順で使う。`satisfying_states` は元の model 順で状態 ID を返す。`certificate` は parity の位置戦略証拠を返し、`checked(compilation, certificate)` は同じ concrete game 上で検査する。

`Formula` は以下の NNF に限定する。

- `Truth(Bool)` と `Proposition(id, positive)`。`positive=false` は負の atomic proposition。
- `And`、`Or`、単一の無ラベル遷移関係に対する `Diamond`、`Box`。
- `Mu(body)`、`Nu(body)`、`Bound(index)`。`Bound(0)` は直近の binder、`Bound(1)` は一つ外側を指す de Bruijn index。

Bound や複合式に適用する一般の Negation constructor はないため、再帰変数の出現は型の構文で正に限定される。許す演算はいずれも集合変数について単調であり、least / greatest fixed point を持つ。閉じていない Bound は `UnboundVariable(index)` で拒否する。空モデルや到達不能な枝の内側でも scope 検査を省略しない。

Kripke の状態・命題 ID は任意の symbolic Nat。状態 ID の重複、未定義遷移先、命題ラベルの重複を拒否する。同じ successor を繰り返した入力は relation として重複除去する。空モデルと dead end は受理する。`holds` に未知の状態 ID を渡すと `None`。

## 評価ゲームへの写像

構文を preorder で flatten し、**同じ式の値が複数箇所に現れても occurrence を区別**する。各 occurrence の Bound は、その lexical environment にある一意な binder node へ解決する。sibling 内の binder がもう片方の scope へ漏れず、名前の shadowing に相当する状況も index だけで区別できる。

n 状態・N occurrence から、ちょうど `n*N+2` 個の parity position を作る。状態の入力順を ordinal、構文 occurrence の番号を node として、ID は `ordinal*N+node`。状態 ID と内部 game ID は混同しない。二つの追加 position は true / false の self-loop sink。

| 構文 | owner | 移動 |
| --- | --- | --- |
| And | OddPlayer（反証側） | 左または右の子 |
| Or | EvenPlayer（検証側） | 左または右の子 |
| Diamond | EvenPlayer | successor 状態上の子 |
| Box | OddPlayer | successor 状態上の子 |
| binder / Bound | EvenPlayer、選択肢は一つ | 本体 / 解決済み binder |
| 真偽・atomic proposition | EvenPlayer、選択肢は一つ | その状態での値に対応する sink |

true sink は priority0、false sink は priority1。**dead-end Diamond は false sink、dead-end Box は true sink** へ移す。これにより空集合上の存在は偽・全称は真という modal semantics を、total parity arena に保つ。非 serial モデルにおける μ-calculus 自体の規約であり、serial を仮定する別ロジックの temporal abbreviation と無条件には同一視しない。

## 最大反復 priority と固定点

parity solver は「無限に繰り返す priority の**最大値**が偶数なら Even 勝利」の規約。式全体の binder 個数を B、囲む binder の個数を d（最外側0）として、binder node に次を割り当てる。

- `Mu`：`2*(B−d)+1`（奇数）
- `Nu`：`2*(B−d)`（偶数）
- その他の構文 node：0

内側 binder より外側 binder が必ず大きくなる。Bound の帰辺は binder を通るため、binder priority を付けるこの方式は反復変数に priority を付ける方式と同じ支配関係を持つ。これは最小 alternation index を求める最適化ではなく、必要な優先順を保つ単純な番号付けである。

max convention の `Ω(μX.φ)=2*nd+1`、`Ω(νX.φ)=2*nd` と、再帰経路上の内側 binder の priority が小さい条件は [Hofmann–Rueß, Certification for μ calculus with winning strategies,2014, §2 Lemma1 / §3.2](https://arxiv.org/pdf/1401.1693) で確認した。文献の依存関係に基づく nd と、この実装の B−d は同じ数値ではなく、こちらは lexical nesting 全体に対してより強い順序を課している。

外側で反復する最も重要な binder が ν なら検証側、μ なら反証側が勝つという評価ゲームの adequacy は [Afshari ほか, Proof Systems for Two-Way Modal μ-Calculus, §2.3 / Theorem2.5](https://www.cambridge.org/core/journals/journal-of-symbolic-logic/article/proof-systems-for-twoway-modal-mucalculus/428EBC95D512384C067BD4C0BB5910AC) でも確認した。上の番号付けがこの支配関係を保つことが、本実装側の適用上の判断である。

例として `Mu(Nu(Bound(1)))` は最外 μ が反復して偽、`Nu(Mu(Bound(1)))` は最外 ν が反復して真。対して `Mu(Nu(Bound(0)))` は内側 ν だけが反復して真、`Nu(Mu(Bound(0)))` は内側 μ だけが反復して偽。priority の向きと scope の両方を試験した。

## 独立 oracle と有限な検証範囲

[MoonBit テスト側の interpreter](../../src/mucalc/mucalc_wbtest.mbt) は状態集合を machine integer の bit mask で表し、And / Or を積・和、Diamond / Box を存在・全称 predecessor として直接評価する。μ は空集合、ν は全状態集合から、現在の環境の下で本体を反復する。**外側の近似値が変わるたび、内側の固定点は bottom / top から新しく計算し直す**。parity game、priority、attractor、戦略は使わない。

[Python generator](../../tools/generate_mucalc.py) は別に `frozenset` の同じ意味論を実装し、[144 fixture](../../src/mucalc/oracle_wbtest.mbt) を生成する。反復ごとに単調性を数値側でも検査する。両 interpreter の反復上限は n+2 回で、有限集合束の高さに基づく。未収束は失敗とし、近似値を最終結果として返さない。

| 範囲 | 検査内容 |
| --- | --- |
| 0～2状態、命題一個 | 全 edge relation・全 labeling の69モデルと、構文サイズ≤3の全134閉 NNF 式。9,246 compiled game が集合意味論と一致 |
| 3状態、命題一個 | 全512 graph×全8 labeling。到達・安全・交互固定点の8式に対する32,768 game が一致 |
| 2状態、命題二個 | 全16 graph×全16 labeling。三 binder の交互固定点・別の内側 binder から共通外側変数を参照する3式と各双対、1,536 game が一致。集合上の complement duality も検査 |
| Python fixtures | 3～7状態・命題二個・固定 seed。通常 ID と sparse ID の両方で144例を照合。最大22 occurrence、5 binder、156 parity positions |
| 構造・境界 | 不正 scope、sibling scope、空モデル、dead end、負の命題、重複 edge の canonical 化、任意 ID、binder priority、全 solver fuel 境界、証拠の改竄 |

## 証明書と compiler の信頼境界

parity の Complete 経路は独立した [cycle checker](../../src/parity/check.mbt) を通る。`checked` も、region の分割・閉包、位置戦略、および不利な最大 priority を持つ cycle がないことを concrete game 上で検査する。偽の region、消した戦略、true 用の証拠を false の game に渡す場合を拒否する。

**この証拠は式から game への compiler の正しさを証明するものではない。** Model の正規化、scope 解決、owner、edge、priority、結果の ID 対応を誤れば、別の game に対する正しい証拠になり得る。この層は compiler の信頼境界として残り、独立集合意味論との有限差分、具体的な node / edge 検査で根拠を追加している。checker と compiler の形式検証や、全論理式に対する機械的証明は主張しない。

## fuel・規模・実行記録

`run` / `step` の fuel はそのまま parity solver の frame step。ゼロなら Paused、尽きた継続は再開でき、最終 Complete を推測しない。`model` / `compile` は fuel の外で有限の入力全体を処理する。frame の内部、証拠 checker、Nat / Chain の走査には入力依存の時間があるため、fuel は壁時計・体積・メモリの上限ではない。試験では一回10,000 solver steps、専用境界試験では明示した1,024 steps を上限にした。

product game は n*N+2 positions、priority は最大2B+1となる。model と式が大きくなれば、game の明示的な構築、単純な occurrence 複製、既存 Zielonka solver と cycle checker が負担になる。API に固定の machine-size 上限は設けていないが、ここでの最大156 positionsを超える一般的な性能・停止時間は検証していない。
