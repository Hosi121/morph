# 二元 BCH 符号の構成と代数的復号（2026-11-16）

[研究記録](README.md) / [生成 API](../../src/bch/pkg.generated.mbti)

目的は、既存の有限拡大体と Berlekamp–Massey を組み合わせ、機械数値を使わずに**実際の二元符号**を構成・符号化・復号できるかを確かめること。実装は [src/bch](../../src/bch/bch.mbt)、検査器は [validation.mbt](../../src/bch/validation.mbt)。RS の符号語を二元と呼び替える実装にはしていない。メッセージ、生成多項式、符号語はすべて `Chain[Bool]` である。

## 対応範囲と規約

`plan(field, root, length, errors)` は次を要求する。

- `field` は既存 `galois` の証明書付き有限拡大体 GF(2^m)。標数が二以外なら拒否する。
- `length = n = 2^m − 1 > 0`。`root = α` は同じ体に属し、位数が**ちょうど n** でなければならない。全正冪を走査し、より早い一への帰還を拒否する。
- 訂正半径 `t = errors` は `2t < n`。`t=0` は生成多項式一の全二元空間として扱う。GF(2) の長さ一もこの場合に含む。
- 根は α¹,…,α²ᵗ。primitive / narrow-sense / full-length に限定する。短縮、非 primitive 長、消失、軟判定は扱わない。

チェーンの添字 i は x^i の係数。生成多項式の次数を r とすると、長さ k=n−r のメッセージ m は `x^r m + (x^r m mod g)` によって系統符号化される。先頭の r ビットがパリティ、後続 k ビットが元のメッセージであり、高次の零も固定長で保持する。

巡回符号を低次からの係数列で表し、生成多項式の次数を n−k とする規約は [Barg / Belding, Lecture13（UMD）](https://user.eng.umd.edu/~abarg/626-2009/notes2005/lecture13.pdf) に対応する。

## 構成で確かめること

α¹,…,α²ᵗ の各未処理の根について、Frobenius 写像 a↦a² の軌道を最初の根へ戻るまで列挙する。体の拡大次数 m を上限とし、重複する軌道は再利用する。各軌道 O について拡大体上で `∏(x+a), a∈O` を計算し、**すべての係数が同じ体の零または一に等しいことを検査してから** `Bool` に戻す。異なる軌道の最小多項式を Boolean 多項式として乗じたものが g になる。

この方法は最小多項式の既製表を保持しない。拡大次数に満たない軌道もそのまま扱う。例えば GF(16) の α⁵ の軌道長二、GF(64) の α⁹ の軌道長三、α²¹ の軌道長二を検査している。既約な定義多項式の不定元が primitive であるとは仮定せず、x⁴+x³+x²+x+1 の不定元（位数五）を拒否し、同じ体の別の primitive 元を受理する試験もある。

`minimal_polynomials(plan)` は共役列と二元係数を返す。`check_minimal_polynomial` は完全な軌道と係数への復元を再検査する。`validate(plan)` は標数、元の所属体、primitive 長、厳密な位数、指定根、逆冪列、最小因子、因子の積、`g | (x^n+1)`、次元の十項目を個別に返す。`valid` が全項目の論理積を取る。これは構成の整合性検査器であり、形式証明ではない。

共役類、最小多項式、その LCM による BCH 構成および標準 (15,7,5) の例は [Gulliver, Minimal Polynomials and BCH Codes（UVic、slides2–9,22,32–35）](https://www.ece.uvic.ca/~agullive/bchcodes-2013.pdf) に対応する。

## 復号と独立した結果検査

シンドロームは `S_j = r(α^j), j=1,…,2t`。既存 `recurrence.checked_berlekamp_massey` に S₁,…,S₂ᵗ を渡す。接続多項式は `Λ(z)=∏(1+α^i z)` であり、その零点 α^(−i) を全位置で評価する Chien 探索から誤り位置 i を得る。二元誤りの値は一なので位置のビットを反転する。RS の誤り値計算や Forney は必要ない。

接続多項式と BCH 復号を線形再帰へ帰着する考え方は [Massey, Shift-Register Synthesis and BCH Decoding, IEEE IT15(1),122–127,1969（著者の ETH アーカイブ）](https://www.isiweb.ee.ethz.ch/archive/massey_pub/pdf/BI411.pdf) を参照した。位置規約は [Gulliver, Decoding BCH Codes（UVic、slides7–11）](https://www.ece.uvic.ca/~agullive/berlekamp-2013.pdf) の (31,16,7) Example9-4（受信多項式 1+x⁹+x¹¹+x¹⁴、誤り位置13,16,19）とも一致した。

次数超過、根の個数の不一致、または訂正後の検査失敗で `Uncorrectable` を返す。成功を返す前に以下を検査する。

- `check_codeword`：Boolean 多項式の除算による g での割り切れと固定長。
- `check`：メッセージの再符号化、受信語との実際の相違位置、位置メタデータの一致と個数≤t。BM や Chien は実行しない。

t を超えた誤りについて元のメッセージの復元や全誤り検出は保証しない。BCH(15,7,5) で零符号語に加えた全455通りの三ビット誤りは、275通りが `Uncorrectable`、180通りが別の距離二以内の符号語への訂正だった。別の有効符号語そのものを受信すれば、零シンドロームの成功になる。この限界も試験に含めている。

## 独立オラクルと検証結果

[MoonBit の数値テスト](../../src/bch/bch_wbtest.mbt) は整数の carryless 多項式演算を使う。最小多項式は軌道から作らず、次数順に全 monic 二元多項式を列挙して指定元で零になる最初のものを探し、gcd/LCM で生成多項式を導く。復号の対照は符号語全列挙による距離≤t の近傍探索であり、BM を再実装していない。

[Python オラクル](../../tools/generate_bch.py) は任意長整数を使い、[14件の固定 fixture](../../src/bch/oracle_wbtest.mbt) に生成多項式、符号語、シンドローム、誤り位置から直接乗じたロケータを出力する。定義多項式の既約性と根の位数、生成多項式の割り切れも数値側で確認する。生成・検査は外部ライブラリ不要で、`--check` は MoonBit formatter が付ける空白・任意末尾コンマだけを無視する。

| 対象 | 照合した範囲 |
| --- | --- |
| n=3,t=1 / n=7,t=1,2,3 | 全メッセージ×全訂正可能マスク、および全受信語の近傍判定 |
| BCH(15,7,5),t=2 | 全128メッセージの符号化、全121訂正可能マスク、全32,768受信語と近傍オラクルの一致。全非零符号語から実最小距離五も確認 |

## 判断と制約

確認できたのは、既存の証明書付き拡大体と checked BM の API をそのまま合成し、生成多項式の F₂ への復元と真の二元符号語を保持した BCH を実装できること、および小さい全入力空間で独立した近傍判定と一致すること。新しい符号理論上の結果や性能優位は主張しない。

制約は full-length primitive binary、narrow-sense、誤りのみの hard decision。API には機械的な長さ上限を設けていないが、ここで実行した最大長は255であり、大規模長に対する時間・再帰深さの保証はない。位数検査は n 回、シンドロームと Chien は概ね n×t 回、BM は概ね t² 回の拡大体演算を必要とし、実際のコストには純記号表現による演算・チェーン走査が加わる。報告した試験時間を復号器だけのベンチマークへ読み替えない。

テスト開発中、MoonBit の固定幅整数で47次の生成多項式を保持しようとしたオラクル側のオーバーフローを検出した。固定幅オラクルをその範囲から外し、(63,16) と (255,223) の係数列は Python 任意長整数の生成 fixture で照合するようにした。kernel 側は最初から Boolean チェーンであり、この数値幅制約を持たない。

共有 package、ルート文書、既存 generator は変更していない。統合側で研究記録の入口、inventory、catalog と通常 check への generator 登録を追加する。ローカル branch のコミットまでを到達点とし、push、merge、deploy は行わない。worktree と `.tools/bch-20261116` は統合担当が成果物を保存するまで維持する。
